# R241 — Windows dynamic-code mitigation versus Linux executable mappings

Status: **research only** (2026-11-22). No Windows reference run, Linux probe, implementation, or security guarantee.

## Architectural question
Can a Linux-hosted NT process truthfully expose Windows process dynamic-code mitigation, including per-thread opt-out and remote downgrade, without confusing guest policy with Linux memory protection?

## VERIFIED — documented interface contracts

1. Microsoft defines `ProcessDynamicCodePolicy` among process mitigations queried by `GetProcessMitigationPolicy`; its documented purpose is preventing dynamic-code generation or modification of existing executable code when enabled. The query takes a process handle with `PROCESS_QUERY_INFORMATION`, policy selector, buffer and length. [M1]
2. The `PROCESS_MITIGATION_DYNAMIC_CODE_POLICY` flags distinguish `ProhibitDynamicCode`, `AllowThreadOptOut`, `AllowRemoteDowngrade`, and `AuditProhibitDynamicCode`. Microsoft explicitly cautions that thread opt-out is **not** a strong-security configuration; remote downgrade allows non-AppContainer processes to relax the calling process's dynamic-code settings. [M2]
3. `SetProcessMitigationPolicy` documents programmatic mitigation changes and advises applying policies before or during initialization. Its documentation explicitly says ASLR policy cannot be made less restrictive after application; **do not extrapolate that ASLR rule to every dynamic-code flag**. [M3]
4. Linux `mprotect` changes page access permissions, and Linux documentation explicitly notes that existing executable mappings can be made writable. This syscall alone does **not** establish a Windows-equivalent process-wide dynamic-code prohibition. `READ_IMPLIES_EXEC` can also change the effective meaning of `PROT_READ` depending on host process state. [L1]
5. Linux's `MFD_NOEXEC_SEAL` creates a non-executable memfd and seals addition of execute permission; `MFD_EXEC` requests an executable memfd. The documented `vm.memfd_noexec` namespace policy governs memfd creation, **not all anonymous mappings or arbitrary executable memory transitions**. [L2] Kernel source also distinguishes shared write-sealed mappings from private mappings. [L3]

## INFERENCE / candidate boundary (not established compatibility)

Maintain guest mitigation policy as a process-owned state object with explicit per-thread exception state and policy-authorized remote updates. Route all **guest-visible** virtual allocation/protection, executable section mapping, image loading and code-patching paths through one policy decision layer. Host `mprotect` and memfd sealing remain backend mechanisms; they cannot be used as a substitute for guest authorization. This is a proposed design, not a proven complete interception boundary.

In particular, a host process retaining unrestricted direct Linux `mmap`/`mprotect` syscalls could bypass a guest-only policy layer. Whether syscall interception and host confinement can close that gap must be proven before describing the policy as a security mitigation. The existing SUD/interception and process-isolation studies are dependencies, not proof.

## OPEN — prioritized falsification gates

- **Windows reference:** Query and set each documented flag combination on supported Windows builds; record exact Win32 errors, buffer-size behavior, inherited versus creation-time settings, and the difference between reporting and enforcing policy.
- **Transition matrix:** Attempt guest `VirtualAlloc`, `VirtualProtect`, executable image/section mappings, writable-to-executable transitions, modification of already executable pages, and code generated by a JIT. Compare before/after mitigation, with thread opt-out enabled/disabled and from another authorized process.
- **Authority:** Probe process-handle access checks, non-AppContainer remote downgrade, cross-thread changes, and races between policy update and mapping/protection. Distinguish documented behavior from observed Windows-version-specific behavior.
- **Host escape:** In an isolated disposable Linux test process, attempt direct `mmap`, `mprotect`, file-backed executable mapping, memfd creation, and raw syscalls after guest policy activation. Treat any bypass as a failed security claim, not merely a compatibility issue.
- **Kernel variance:** Record architecture, kernel version, personality flags, `vm.memfd_noexec`, LSM/seccomp configuration and `MFD_*` support. Explicitly compare private versus shared memfd mappings; do not assume seals control all mapping types.
- **Failure semantics:** Map host `errno` to guest API errors only after Windows differential evidence. Never assert that a host `EACCES` corresponds to a particular NTSTATUS without testing.
- **Cross-component:** Verify that loader relocations/import fixups and runtime exception/unwind infrastructure can initialize under policy without leaving writable-executable gaps. Track code-cache and JIT needs separately.

## Decision impact

This issue is a **security/architecture gate** for ADR-003: pure user-space mediation is a candidate for API compatibility, but strong enforcement requires evidence that untrusted guest machine code cannot evade the mediator using Linux syscalls or alternate mappings. No kernel extension is selected here.
